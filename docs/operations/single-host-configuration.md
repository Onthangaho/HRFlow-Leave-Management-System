# Single-host configuration and local verification — issue #81

Checked 9 October 2026. Supported target: one organisation, one host, persistent **local** filesystem with reliable OS locking, self-hosted Kestrel behind an explicitly trusted TLS proxy or with direct TLS. Multiple API/worker processes on that same host must share the same absolute database path and secrets. This is not evidence of actual staging/production hosting. Hosting vendor, capacity and costs remain open; no free-tier capability or pricing is assumed.

SQLite serializes writers database-wide. Existing protected operations acquire `BeginTransaction(deferred: false)` before authoritative reads, with a three-second connection/command timeout. Microsoft.Data.Sqlite can retry acquiring SQLite locks within that timeout; HRFlow does not replay the application callback. Expected contention returns 409; clients must refresh and deliberately retry. Deferred reporting snapshots do not reserve a writer. Normal connection defaults are distinct from the protected three-second override. No multi-host/shared-network-file support. Changing providers requires equivalent transaction protection, migrations and verification, not merely a connection string.

Sources checked on this date: [Microsoft transactions](https://learn.microsoft.com/en-us/dotnet/standard/data/sqlite/transactions), [lock/timeout handling](https://learn.microsoft.com/en-us/dotnet/standard/data/sqlite/database-errors), [SQLite network caveats](https://www.sqlite.org/useovernet.html), [ASP.NET trusted proxies](https://learn.microsoft.com/en-us/aspnet/core/host-and-deploy/proxy-load-balancer?view=aspnetcore-8.0). These establish mechanisms, not HRFlow load capacity.

## Required configuration

Use environment variables or an approved deployment secret store. Never commit secret values. HS256 uses the UTF-8 bytes of SigningKey, not a decoded base64 key. Generate at least 32 random bytes and represent them as 64 hexadecimal characters, independently for signing and refresh pepper. Startup rejects missing issuer/audience, short/repetitive secrets and known demonstration markers. Validation cannot prove randomness; operators must generate secrets securely. Signing algorithm is explicitly restricted to HS256. Existing expiry/skew (30 seconds), current-role and credential-version checks remain intact. Signing-key rotation invalidates old access JWTs; pepper rotation invalidates old refresh tokens but does not alone invalidate already-issued access JWTs. Coordinate all processes.

Non-Development requires HTTPS Activation:ApplicationOrigin (trusted scheme/host/optional port, no path, credentials, query, fragment or trailing slash), explicit AllowedHosts, and optional exact HTTPS Deployment:CorsOrigins. An empty CORS list supports same-origin hosting; CORS does not authorize API access. Development retains loopback client origins. Production rejects any Seeding configuration and Activation:Delivery. Production onboarding/resend remains unavailable until an approved provider is implemented; no local pickup workaround.

Proxy handling is disabled by default. Enable Deployment:ProxyEnabled only with an explicit list of individual KnownProxies IPs; one forwarded hop is accepted for scheme/client IP. No forwarded Host trust. The edge must strip incoming forwarded headers, enforce Host, terminate TLS, and restrict backend access with bind/firewall rules. Do not enable ASPNETCORE_FORWARDEDHEADERS_ENABLED or clear proxy trust lists. HTTP application requests are redirected when an HTTPS endpoint is known, otherwise denied; trusted proxy-reported HTTPS is supported. Health probes should use TLS or follow the configured HTTPS redirect. When no redirect endpoint is configured, health endpoints may be probed over the private backend connection; application endpoints still reject HTTP. Integrated server/platform proxy behavior requires separate verification.

## Persistent storage and permissions

Non-Development requires Storage:LocalFileSystem=true as an operator acknowledgment, an existing absolute SQLite path with Mode=ReadWrite, and an existing absolute Storage:PrivateFilesRoot. Both must be outside application/content/static roots. UNC, detected network drives, URI/in-memory connections, shared cache and symlink/reparse-point paths are unsupported. Validation checks write access using isolated delete-on-close probes, never resets or repairs the database. It cannot certify a volume's locking/durability, mount persistence, ACL privacy or later mount replacement. Operators must verify those separately.

Give the service identity directory rights for SQLite journals/WAL/SHM and private storage, but no public read access. Do not place the database or future files inside wwwroot, SPA dist, build/publish folders, source checkout or publicly served proxy aliases. PrivateFilesRoot is a reserved location only: uploads/file serving are not implemented. Persistent volumes must survive process/container replacement; ephemeral disks and remote shares are not supported. Startup does not create missing Production directories or databases.

## Migrations and first administrator

Both DatabaseSeeder.SeedAsync and DevelopmentIdentitySeeder.SeedIdentityAsync exit outside Development, before migrations/credentials/data changes. Development automatic migrations are only supported with one startup process; finish startup before launching another. Production uses explicit offline migrations, never automatic startup migration or seed repair. DesignTimeDbContextFactory requires ConnectionStrings__DefaultConnection explicitly and boots no API, workers or seeds; offline schema tooling intentionally bypasses runtime certificate/private-storage guards. Operators still own backup/path/access validation. /health is liveness only; /health/ready returns 200 only when the database is reachable and all migrations are applied, otherwise generic 503. Neither returns paths/schema/credentials. Readiness is not a full business-data integrity or load check.

Stop every API/worker writer. Take a consistent SQLite backup with WAL-aware backup tooling, plus a separately protected private-file backup. Verify restoration on an isolated copy **before** upgrading. Review migration SQL and rollback data loss. Run `dotnet ef database update --project src/HRFlow.Infrastructure --startup-project src/HRFlow.Api --connection $env:ConnectionStrings__DefaultConnection` from an operator-controlled environment, then restart and check readiness/history. For a new store the offline operator may use Mode=ReadWriteCreate during migration only; runtime requires ReadWrite. Do not copy a live database file alone or run migrations concurrently with writers. The subsequent #82 slice provides [operator commands and recovery policy](backup-restore.md), with [measured local restore evidence](../verification/verified-backup-restore.md). Scheduled backup automation and real deployment recovery remain unimplemented.

First-administrator provisioning remains an explicit **unimplemented deployment gate**: a reviewed offline one-time tool must refuse a nonempty Identity store, use Identity validators and protected atomic persistence, and create an activated HR/profile with a securely operator-supplied initial credential (never a default/public registration). It must not restore roles/reactivate or reset any existing account. Configure its initial department explicitly. This phase verifies only preexisting synthetic activated accounts copied into disposable Production-mode storage; it does not implement or verify first-admin provisioning. Do not deploy a fresh installation until this gate and approved invitation delivery are resolved.

## SPA and reproducible local Production-mode checks

The API does not serve SPA assets in this change. Build the SPA with VITE_API_BASE_URL set to `/api/v1` for same-origin edge routing, or the explicit HTTPS API base for separate origins. Configure the chosen static server to serve index.html for non-API client routes, never for /api or health. Prevent SPA fallback from exposing private directories. Static-server fallback and hosting integration remain unverified.

Use a disposable directory outside the checkout, copied synthetic database, local-only certificate and private configuration. The placeholder [template](production-environment.example.ps1) is documentation, not runnable defaults. Load real values privately, then:

```powershell
$env:ASPNETCORE_ENVIRONMENT = 'Production'
dotnet build HRFlow.sln
dotnet src/HRFlow.Api/bin/Debug/net8.0/HRFlow.Api.dll
```

Set certificate path/password privately when using direct TLS. Trust a local certificate only for the disposable browser context; certificate-verification bypass must never be configured in the application or deployed client. Development is distinct: seeding and private pickup are local demonstration facilities. Production-mode locally proves startup/API behavior, not hosting/TLS issuance/network hardening or business compliance.

Logs retain safe request/action/correlation identifiers and outcome categories, never bodies/query strings, passwords, activation links, phone/profile contents or medical evidence. Hosting lifetime path announcements are reduced to Warning. Protect logs and rotate them separately. [Executed results and outstanding gates](../verification/safe-deployment-configuration.md).
